# document-writer

A portable, manually installed extension for any [OpenCode](https://opencode.ai) project that has the [oh-my-opencode-slim](https://www.npmjs.com/package/oh-my-opencode-slim) plugin. It adds a two-agent document workflow with an Oracle evidence-review loop:

- **document-writer** — bounded creation and editing of formal product and engineering documents (PRDs, technical solutions, architecture/interface designs, delivery documents, ADRs), dispatched with one explicit mode: `MODE: WRITE` for creation/body edits, `MODE: REVIEW` for expression, structure, document-internal consistency, audience fit, and readability (returns `PASS | REJECT | BLOCKED` with findings bound to the inspected revision and its retained reply; never certifies protocol/technical semantics). Writing follows a layered read-back after each editing round plus a final whole-document verification; a `DONE` result is returned once, with the content location and a retrievable revision (or readable retained snapshot) plus its hash for every substantive edit. A plain `DONE` covers writing and self-check only — it excludes independent review and publication.
- **lark-operator** — all Feishu/Lark reads and operations except formal document bodies: writer-side Lark body editing happens only in document-writer under explicit user opt-in with compatible granted skills, and is unavailable otherwise — never through lark-operator. Every write or external effect requires explicit user authorization (otherwise `NEEDS_AUTHORIZATION`); authorization transfers from the original task, so a dispatched task that states its scope, recipients, content, and permitted effects — traceable to explicit user consent — runs without per-API re-asking, while missing or exceeded authorization still returns `NEEDS_AUTHORIZATION`. Oracle approval applies additionally when requested or for impact-gated categories — security/privacy/permissions, breaking contracts, irreversible/high-loss actions, formal approvals, external legal/commercial/SLA commitments (missing approval → `NEEDS_REVIEW`). Platform or API choice alone does not trigger review. WebFetch is permitted solely for official Feishu/Lark API documentation needed by dispatched operations — never as general web access. Optional integration: it ships capability-less and is populated only from `lark-*` skills independently installed on the target (none are vendored here).
- **Oracle boundaries** — `prompts/oracle_append.md` makes Oracle review dispatched documents for technical correctness, feasibility, contract consistency, acceptance criteria, and specified risks (expression/structure/audience-fit review belongs to document-writer unless it changes technical meaning), and answer `PASS | REJECT | BLOCKED` once with findings bound to the inspected revision (or readable retained snapshot) plus SHA-256 and a readable source; the host retains each verdict reply as the review record — no separate publication call — and review never issues publication or execution authorization. On rereview, prior findings get explicit dispositions (adopted/verified, adopted/unverified, not adopted/with evidence, deferred/disputed) and review versions link with `related`, never `supersedes`.
- **Council, Orchestrator, and Fixer prompts** — `prompts/council_append.md` adds evidence-and-disagreement judgment to the Council synthesis agent (judge claims by traceable current-version evidence, attribute reported checks to their seats, retain material dissent; when publication tools are unavailable, return attributed findings instead of inventing a record ID; in omo-slim 2.2.21 the append reaches the synthesis agent, not automatically every generated councillor seat); `prompts/orchestrator_append.md` adds the document/review gating policy and mixed-task routing guidance (ordinary document work is accepted after the writer's final full-document self-check — `DONE` excludes independent review and publication; Oracle review is required when requested or for impact-gated categories; each first review starts in a fresh session, rereviews may reuse the reviewer session; the review budget is one initial review plus at most two rereviews per review objective, counted across sessions — exhaustion is reported and escalated to the user, never treated as `PASS`, and renaming an objective does not reset the budget; resolve internal bookkeeping labels into user-understandable references before replying); `prompts/fixer_append.md` treats the dispatched brief and its referenced sources as the complete working context and gives the built-in fixer a final handoff step — return one result with the changes, the verification actually performed, and explicit limits, reusing existing records rather than publishing duplicates, including for blocked or no-change outcomes. Review ownership holds across roles: an independent verdict stays attributable to its original reviewer, and supplementary verification by the coordinating role cannot turn that reviewer's `BLOCKED`/`REJECT` into `PASS`.
- **Result delivery without a publication tool** — long results may be returned as citations of retained records only after the host confirms author, message, byte-exact content, and receiver readability; otherwise the full original text is returned, and original records are never rewritten. This citation capability is a **host** feature (BCP plugin plus host integration): installing this portable template alone does not provide it. Without that integration, agents return complete original replies and never fabricate citations, receipts, or record IDs. Host retention follows the host's announced convention and is a work record, not business publication. Sending a document or result to external recipients is a separate authorized operation using the destination's supported interface. When no publication mechanism is available, agents return usable results with stated limits rather than claiming a published handoff.

## Effective-source rule

An agent's effective prompt and config come from the highest-priority source that defines them — plugin config layers (user then project, per-key merges), the active preset's member, inline `agents.<name>.prompt` overrides, and the host's native agent definitions each cover different fields. A native agent file (host or project `.opencode` `agent/`/`agents/` directory) covers its own body prompt and frontmatter fields and shadows plugin-layer copies for those fields; on setups that define `lark-operator` natively, that file — not `prompts/lark-operator.md` in this repo — is the effective body (INSTALL §2 step 8). Package presence does not imply an active entry: the TUI plugin and the `server` entry are distinct package entries, either may be a local build, and only the entry OpenCode actually loads counts.

## Pre-write gate and review loop

Shared-document writes carry a **pre-write gate**: authorization for the exact target/scope, plus any required Oracle approval of the current revision — without it the writer works only in an authorized draft location. Ordinary document work then completes on the writer's final full-document self-check. When post-write review is requested or impact-gated (security/privacy/permissions, breaking contracts, irreversible/high-loss actions, formal approvals, external legal/commercial/SLA commitments), the loop is: document-writer writes and rereads → Oracle reviews the revision the writer returned → findings return to the same document-writer → the same Oracle rereviews previous findings plus the full delta, within the review budget of one initial review plus at most two rereviews — the coordinating role's supplementary verification never turns the reviewer's `BLOCKED`/`REJECT` into `PASS`, and exhaustion is reported to the user rather than treated as approval. Post-write review never substitutes for the pre-write approval gate.

## Additive by design

The config overlay (`oh-my-opencode-slim.json`) touches only the `agents` section and never switches the preset, pins models, or overwrites a target's existing skills or MCPs:

- Both custom agents set `"inheritModelFrom": "session"` (verified in the omo-slim 2.2.21 and 2.2.25 sources), so they run on the session's model on any fresh target.
- Orchestrator restrictions are added via `agents.orchestrator.skills_remove` (the `lark-*` names plus `humanizer`, `use-modern-go`, and `managing-lark-project-folder`), which resolve into effective exclusions even for `["*"]` lists — the Orchestrator cannot invoke Lark skills directly. The removal names are deliberate guardrails: harmless no-ops while the skills are absent, still effective if they are installed later.
- **No Lark skills are vendored.** `lark-operator` ships with `"skills": []`; INSTALL §6.1 populates it only from skills discovered on the target after an official `lark-cli` install/update, and only after per-skill vetting (role fit, stated prerequisites, available CLI/auth, least-privilege boundaries). A skill is granted only when its WebFetch use stays inside `lark-operator`'s boundary — official Feishu/Lark API documentation for dispatched operations; `lark-openapi-explorer`-style skills needing unrestricted web access stay ungranted with the limitation recorded, permissions are never widened beyond the prompt's stated boundary, and no shell bypass is used to make a skill fit. Other installed cloud-document CLIs are inventoried and wired to matching agents by the same vetted, precedence-safe, reversible procedure — never into `lark-operator` by document-topic affinity. Every discovered platform-document skill name outside the overlay's static list is also added to the Orchestrator's `skills_remove` (INSTALL §6.3), closing wildcard access to newly discovered names. Four further skills (`yogo-products`, `designing-work-loops`, `lark-worklog`, `managing-lark-project-folder`) belong to their owning project's `.agents/skills/` — they are not global dependencies, are not added to the portable template by default, and existing grants for them stay untouched; a target that already grants any of them keeps those grants. Where a target defines `lark-operator` (or any agent) via a native agent file, that file is the effective body — INSTALL §2 step 8 governs which source gets updated.

## Layout

```
oh-my-opencode-slim.json   Additive agents-only overlay (no preset, no model IDs, no MCP grants — both agents carry empty `mcps` lists)
prompts/
  document-writer.md       document-writer agent prompt
  lark-operator.md         lark-operator agent prompt (repo mirror — a target may define this agent natively; see INSTALL §2 step 8)
  oracle_append.md         Document-review contract appended to the Oracle role
  council_append.md        Evidence-and-disagreement guidance for the Council synthesis agent
  orchestrator_append.md   Document/review gating + mixed-task routing for the Orchestrator
  fixer_append.md          Brief-context + reuse-records handoff rule appended to the built-in fixer role
skills/                    4 complete skill directories copied verbatim; no lark-* skills are vendored
README.md / INSTALL.md / SOURCES.md / .gitignore
```

## Requirements

- OpenCode with the oh-my-opencode-slim plugin installed and loaded.
- Lark features are optional: when requested, install or update `lark-cli` by its official method and grant only the skills it actually exposes (INSTALL §6.1). Local document-writer→Oracle verification works without any cloud-document CLI.

Manual installation only — no installer scripts. [INSTALL.md](INSTALL.md) covers effective-config-layer and native-agent-definition detection (only the actually-effective source is updated), backup/reversal records, adaptive steps, and split local vs conditional-Lark verification. Every file's origin is recorded in [SOURCES.md](SOURCES.md).

Tested compatibility, by what was actually run:

- **End-to-end baseline (historical)**: oh-my-opencode-slim **2.2.21** on OpenCode **1.18.31** — a full end-to-end run was tested at that time; it remains the recorded baseline, not a hard requirement. The config-resolution behavior this overlay depends on was additionally re-checked against the **2.2.25** source.
- **Current portable load test (2026-09-30)**: on oh-my-opencode-slim **2.2.25** with OpenCode **1.18.33**, the overlay loaded in a fresh configuration with **zero model calls**, passing checks for precedence-safe array override (a project exclusion wins without reviving a user exclusion), all six copied prompts being effective, Oracle and lark-operator artifact-mutation denials, official-document-only WebFetch capability, and no change to the live configuration (`/tmp/opencode/orchestration-refresh/live/portable-final/PASS.json`, overlay SHA-256 `bb1ab25827469fc6e6963b2219f69a69da24ad1f6fa63d56496d02e30d19ce08`).
