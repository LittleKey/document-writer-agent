# omo-coworkers

**omo-slim handles the code. This project adds the multi-agent orchestration for the rest of your daily work — additively, reversibly, always tracking upstream.**

「代码之外的多 agent 办公编排，增量叠加于 omo-slim。」

omo-coworkers is an additive orchestration extension on top of oh-my-opencode-slim (OMO) — not a fork, and not a pile of agents. Delivered today: reviewed document workflows (the **document-writer** role) plus optional Lark/Feishu operations (the **lark-operator** role). It installs as a reversible overlay into your existing OMO setup, is multi-host deployable, and tracks upstream OMO instead of forking it. The growth direction is reusable orchestration policies for daily work beyond code.

## Design principles

- **Additive-only** — never removes or overrides user config.
- **Fully reversible** — uninstall/rollback restore the original state, drift-gated by recorded hashes.
- **Upstream-tracking** — component-level compatibility matrix instead of pinning.

## Roles and delivery policy

- **document-writer** — bounded creation and editing of formal product and engineering documents (PRDs, technical solutions, architecture/interface designs, delivery documents, ADRs), dispatched with one explicit mode: `MODE: WRITE` for creation/body edits, `MODE: REVIEW` for expression, structure, document-internal consistency, audience fit, and readability (returns `PASS | REJECT | BLOCKED` with findings bound to the inspected revision and its retained reply; never certifies protocol/technical semantics). Writing follows a layered read-back after each editing round plus a final whole-document verification; a `DONE` result is returned once, with the content location and a retrievable revision (or readable retained snapshot) plus its hash for every substantive edit. A plain `DONE` covers writing and self-check only — it excludes independent review and publication.
- **lark-operator** — all Feishu/Lark reads and operations except formal document bodies: writer-side Lark body editing happens only in document-writer under explicit user opt-in with compatible granted skills, and is unavailable otherwise — never through lark-operator. Every write or external effect requires explicit user authorization (otherwise `NEEDS_AUTHORIZATION`); authorization transfers from the original task, so a dispatched task that states its scope, recipients, content, and permitted effects — traceable to explicit user consent — runs without per-API re-asking, while missing or exceeded authorization still returns `NEEDS_AUTHORIZATION`. Oracle approval applies additionally when requested or for impact-gated categories — security/privacy/permissions, breaking contracts, irreversible/high-loss actions, formal approvals, external legal/commercial/SLA commitments (missing approval → `NEEDS_REVIEW`). Platform or API choice alone does not trigger review. WebFetch is permitted solely for official Feishu/Lark API documentation needed by dispatched operations — never as general web access. Optional integration: it ships capability-less and is populated only from `lark-*` skills independently installed on the target (none are vendored here).
- **Builtin-role policy** — the Oracle, Orchestrator, Explorer, Designer and Librarian appends are maintained only in [dotfiles/opencode/oh-my-opencode-slim](https://github.com/LittleKey/dotfiles/tree/master/opencode/oh-my-opencode-slim). This package contains no copies and `coworkers-install` does not install them. Targets that use that personal policy deploy the appends from one selected dotfiles revision; see [INSTALL.md](INSTALL.md#builtin-role-appends-across-machines). The two custom-role prompt bodies remain in this package.
- **Result delivery without a publication tool** — long results may be returned as citations of retained records only after the host confirms author, message, byte-exact content, and receiver readability; otherwise the full original text is returned, and original records are never rewritten. This citation capability is a **host** feature (BCP plugin plus host integration): installing this portable template alone does not provide it. Without that integration, agents return complete original replies and never fabricate citations, receipts, or record IDs. Host retention follows the host's announced convention and is a work record, not business publication. Sending a document or result to external recipients is a separate authorized operation using the destination's supported interface. When no publication mechanism is available, agents return usable results with stated limits rather than claiming a published handoff.

## Effective-source rule

An agent's effective prompt and config come from the highest-priority source that defines them — plugin config layers (user then project, per-key merges), the active preset's member, inline `agents.<name>.prompt` overrides, and the host's native agent definitions each cover different fields. The installer writes the **native agent files** for both roles, so by design they are the effective bodies (v1 `agent/`, v2 `agents/`; INSTALL §1, §5 — the recorded runtime checks observed this **without the OMO plugin loaded**, so combined native+OMO precedence is owner-validated separately); where a target already defines either role natively, the installer refuses to shadow it and reports a conflict instead (INSTALL §3). Package presence does not imply an active entry: the TUI plugin and the `server` entry are distinct package entries, either may be a local build, and only the entry OpenCode actually loads counts.

## Pre-write gate and review loop

Shared-document writes carry a **pre-write gate**: authorization for the exact target/scope, plus any required Oracle approval of the current revision — without it the writer works only in an authorized draft location. Ordinary document work then completes on the writer's final full-document self-check. When post-write review is requested or impact-gated (security/privacy/permissions, breaking contracts, irreversible/high-loss actions, formal approvals, external legal/commercial/SLA commitments), the loop is: document-writer writes and rereads → Oracle reviews the revision the writer returned → findings return to the same document-writer → the same Oracle rereviews previous findings plus the full delta, within the review budget of one initial review plus at most two rereviews — the coordinating role's supplementary verification never turns the reviewer's `BLOCKED`/`REJECT` into `PASS`, and exhaustion is reported to the user rather than treated as approval. Post-write review never substitutes for the pre-write approval gate.

## Additive by design

The config overlay (`oh-my-opencode-slim.json`) touches only the `agents` section and never switches the preset, pins models, or overwrites a target's existing skills or MCPs:

- Both custom agents set `"inheritModelFrom": "session"` (verified in the omo-slim 2.2.x and 3.0.1 sources), so they run on the session's model on any fresh target — no model IDs are pinned and no personal models are carried.
- The effective prompts for both roles are the **host-native agent files** the installer writes (v1 `agent/` + grouped `permission` map, v2 `agents/` + `permissions` array with the 2.0 action names), bodies byte-identical to `prompts/document-writer.md` / `prompts/lark-operator.md`. The overlay carries no prompt text and the installer writes no OMO prompt-dir copies, so by design each role's effective prompt is the native agent file on either host (observed as the verbatim prompt on 1.18.33, 1.18.35 and 2.0.20 in checks that ran **without the OMO plugin loaded**; those checks do not by themselves establish combined native+OMO precedence — owner-validated separately).
- **No Lark skills are vendored.** `lark-operator` ships with `"skills": []`; INSTALL §6 covers populating it only from skills discovered on the target after an official `lark-cli` install/update, and only after per-skill vetting (role fit, stated prerequisites, available CLI/auth, least-privilege boundaries). A skill is granted only when its WebFetch use stays inside `lark-operator`'s boundary — official Feishu/Lark API documentation for dispatched operations; `lark-openapi-explorer`-style skills needing unrestricted web access stay ungranted with the limitation recorded, permissions are never widened beyond the prompt's stated boundary, and no shell bypass is used to make a skill fit. Other installed cloud-document CLIs are inventoried and wired to matching agents by the same vetted, precedence-safe, reversible procedure — never into `lark-operator` by document-topic affinity. Four further skills (`yogo-products`, `designing-work-loops`, `lark-worklog`, `managing-lark-project-folder`) belong to their owning project's `.agents/skills/` — they are not global dependencies, are not added to the portable package, and existing grants for them stay untouched. Where a target already defines either role via a native agent file, that file is a conflict the installer refuses (never silently shadowed); reconcile deliberately (INSTALL §3).

## Layout

```
oh-my-opencode-slim.json   Additive agents-only overlay (no preset, no model IDs, no MCP grants, no prompt text — both agents carry empty `mcps` lists)
bin/coworkers-install.mjs  Host-aware installer CLI: install | plan | uninstall | rollback | verify (--json); writes the target manifest `.opencode/omo-coworkers-install.json`
installer/                 Renderer (per-host permission vocabulary), merge, detect, manifest, atomic-write modules
prompts/
  document-writer.md       document-writer agent prompt (prompt authority for the installed native agent file)
  lark-operator.md         lark-operator agent prompt (prompt authority for the installed native agent file)
skills/                    3 complete skill directories copied verbatim; no lark-* skills are vendored
plugins/
  claude-advisor/          Advisor plugin source — installed by the installer (3.1.0+) as `<target>/.opencode/plugins/claude-advisor.mjs`; `guard.test.mjs` is not shipped
test/install.test.mjs      Fixture suite + optional live-host effective-profile checks (OCW_V1_BIN / OCW_V2_BIN)
package.json               npm metadata (v3.2.0; bin: coworkers-install; test: node --test)
README.md / INSTALL.md / SOURCES.md / LICENSE / .gitignore
```

The retired `writing-plans` skill is no longer bundled (approved removal of the two personal plan skills, 2026-10-11) — the package ships the three skill directories above. Reinstalling over an older four-skill installation does **not** delete its already-installed `writing-plans` copy; the upgrade behavior and the ownership-aware removal path are documented in [INSTALL.md §4](INSTALL.md#4-reversal).

## Requirements

- Stable [OpenCode](https://opencode.ai) v1 ≥ 1.18.29 within major 1 (installer-level runtime checks ran on 1.18.33) or v2 ≥ 2.0.20 within major 2 (checks ran on 2.0.20); older v1 hosts and versions outside the matrix — below the v2 2.0.20 floor, unknown majors, pre-releases — are rejected. The oh-my-opencode-slim plugin must be installed and loaded for the OMO overlay to take effect — the native role agents and skills register with the host alone.
- Plugin payload (3.1.0+): installed to `<target>/.opencode/plugins/claude-advisor.mjs`, identical for host v1 and v2, following the official plugin convention — project-level `.opencode/plugins/`, loose JS/TS files auto-loaded at startup (per [opencode.ai/docs/plugins](https://opencode.ai/docs/plugins/), fetched 2026-10-14). Subdirectory layouts are not documented there, hence a single loose file; a config-dir `package.json` is needed only when importing npm packages — ours imports none.
- Advisor role's omo-slim dependency (documented-only, never installer-gated): validated against omo-slim **3.0.4** (latest at writing); `acpAgents` exists across the omo-slim 3.0.x line; the exact introducing version is not verified, so no "requires ≥ 3.0.4" claim is made. This repository's checks verify file placement and hashes (fixture tests), not live per-host plugin loading.
- Install with `npx coworkers-install` — npm package **omo-coworkers**, current release **v3.2.0** (`dw-install` remains as a compatibility alias pointing to the same script, `bin/coworkers-install.mjs`).
- Node ≥ 20 for `bin/coworkers-install.mjs`.
- Lark features are optional: when requested, install or update `lark-cli` by its official method and grant only the skills it actually exposes (INSTALL §6). Local document-writer→Oracle verification works without any cloud-document CLI.
