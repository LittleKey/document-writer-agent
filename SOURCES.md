## Overlay design (syntax verified against omo-slim 2.2.21 source; re-checked against 2.2.25 and the 3.0.1 sources, 2026-09-30)

- **Two managed entries only (2.0.0)** — the installer owns exactly `agents["document-writer"]` and `agents["lark-operator"]`; every other semantic value of the target's overlay file is preserved through the structured merge (the merged file is re-serialized 2-space JSON, so original byte layout is not preserved). The overlay carries no `prompt`/system text: the effective prompt for each role is the host-native agent file the installer writes (v1 `agent/<name>.md` with a grouped `permission` map; v2 `agents/<name>.md` with an ordered `permissions` array using the 2.0 action names — `task`→`subagent`, `bash`→`shell`), body byte-identical to `prompts/<role>.md`. Observed effective on 1.18.33 (`debug agent`) and 2.0.20 (`/api/agent`, isolated host, zero model requests) in checks that ran without the OMO plugin loaded — combined native+OMO precedence is owner-validated separately. Builtin-role appends belong to dotfiles and are not included in this package or its installer payload.
- **`inheritModelFrom: "session"`** on both custom agents — enum `session | orchestrator` per the 2.2.21 schema; the resolver deletes the agent's model so it inherits the session/primary model (`dist/index.js` model-inheritance code; re-checked in 3.0.1). No model IDs are pinned; a fresh target instantiates the agents without model errors. A custom agent entry lacking both `model` and `inheritModelFrom` is skipped with a warning, so keep the field when reconciling.
- **Personal guardrails are not carried (2.0.0)** — the earlier portable `agents.oracle` read-only block and the 32-name `agents.orchestrator.skills_remove` list were owner-side deployment policy; they now live only in the owner's dotfiles configuration. The generic package ships no entries touching upstream agents (`oracle`, `orchestrator`, `council`, `fixer`) — nothing to force-overwrite, nothing to reset.
- **Layer array semantics** — config layers merge with wholesale array replacement (`skills`, `skills_add`, `skills_remove` never concatenate across user→project or preset→`agents`): the effective value of each directive key is the highest-priority layer's array, and an empty array shadows lower layers like any other value. Post-install grant procedures (INSTALL §6) therefore append only their entries to the effective pre-install winning array and never union shadowed lower-priority values; `skills_add` cannot re-enable a skill excluded via `"!"` tokens or `skills_remove`.
- **`agents.document-writer.skills` reduced from live** — the live 2026-09-26 config grants the writer the Lark body-editing set (`lark-doc`, `lark-markdown`, `lark-sheets`, `lark-base`, `lark-slides`, `lark-drive`, `lark-wiki`, `lark-whiteboard`, `lark-shared`) plus `yogo-products`; this overlay keeps only the three bundled grants (`maintaining-product-engineering-docs`, `domain-modeling`, `humanizer`). The Lark set is re-granted on targets only via the explicit opt-in in INSTALL §6; `yogo-products` is excluded by policy.
- **`$schema` stays `@latest`** — the reviewed live config pins the 2.2.25 schema, while the portable overlay retains its existing editor-schema URL. That URL is not a compatibility guarantee for future plugin versions; the tested versions and scope are listed below.
- **No `preset`/`presets`, no `model`/`variant`, no MCP grants, no `council`** — the live config's preset members, provider model IDs (`openai/*`, `newapi/*`), council endpoints, and MCP grants (`gh_grep`, `context7`) are environment-specific and are excluded; both custom agents carry `"mcps": []`, which grants nothing. Per-agent permission denials for `gh_grep_*`/`context7_*` are preserved verbatim.
- **No `lark-*` skills vendored; `lark-operator` ships `"skills": []`** — its Lark capability is populated on the target only from skills discovered after an official `lark-cli` install/update, each vetted for role fit, stated prerequisites, available CLI/auth, and least-privilege boundaries before granting (INSTALL §6). `lark-openapi-explorer` is never grantable to an agent denying WebFetch: it stays ungranted with the limitation recorded, and permissions are never widened or shell-bypassed to make a skill fit (the same vetting governs other cloud-document CLIs, INSTALL §6). Formal Lark document-body editing routes to `document-writer` only under explicit user opt-in with compatible granted skills (INSTALL §6); the writer's result contract (content location plus retrievable revision or retained snapshot and hash) applies, with Oracle review when requested or impact-gated; without the opt-in it is unavailable and never routed through `lark-operator`, which remains forbidden from formal document bodies. The formerly vendored `lark-openapi-explorer` copy was removed with the rest of the `lark-*` set.
- **Config-layer facts documented in INSTALL.md**, verified in `dist/index.js`: user plugin config = first existing `oh-my-opencode-slim.jsonc`/`.json` (`.jsonc` preferred within a dir) across the custom dir (`$OPENCODE_CONFIG_DIR`) and the default dir (`$XDG_CONFIG_HOME/opencode` else `~/.config/opencode`), searched custom-first — a custom dir with no plugin config falls through to the default dir; project config at `.opencode/oh-my-opencode-slim[.jsonc|.json]` merges over user (scalars override, `agents`/`presets` deep-merge); `OH_MY_OPENCODE_SLIM_PRESET` overrides the `preset` key; prompts resolve first-match-winner in the order project preset-dir → project base dir → custom-dir preset-dir → default-dir preset-dir → custom-dir base dir → default-dir base dir, and `agents.<name>.prompt` inline keys override the `<name>.md` file prompt (warning only; `<name>_append.md` still appended).

## Global install run (2026-10-15)

- **Feature under record (`--global` user-level install mode; v3.3.0 code, uncommitted at recording time)**: implemented and fixture-tested — 61 tests: 59 pass, 0 fail, 2 env-gated skips. CLI: `coworkers-install install|plan|verify|uninstall|rollback --global [--config-dir <dir>] [--force]`; `--global` is mutually exclusive with `--target` (exit 1); `--config-dir` (only valid with `--global`) defaults to `$OPENCODE_CONFIG_DIR` or `~/.config/opencode`. Mapping, config-dir-relative: prompt bodies → `oh-my-opencode-slim/<role>.md` (verbatim repo prompts); the three skills → `skills/<name>/` (plural, host-native); overlay → `oh-my-opencode-slim.json` — created wholesale if absent, additively merged if present without managed agent keys, and **preserved completely untouched (even with `--force`)** with a recorded notice when it already defines `document-writer`/`lark-operator`; manifest → `omo-coworkers-install.json` gaining `scope: "global" | "project"` (absent reads as project; schemaVersion stays 1) plus an advisory `notices[]` that `verify` re-surfaces; backups → `omo-coworkers-backup/<stamp>/`.
